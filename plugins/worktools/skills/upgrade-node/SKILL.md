# 升级项目 Node 版本

## 概述

将项目升级到用户指定的 Node 版本：只改核心两处版本声明（`.nvmrc` 与 `package.json` 的 `engines`），用 nvm-windows 安装并切换 Node，重装依赖，运行项目已有脚本做全流程验证，最后输出报告。支持两种模式：

- **单项目模式**：目标是单个项目目录。
- **批量模式**：目标是一个父目录（如 `D:\Workspace\kaizen\fe`），升级其下所有前端项目。

硬性约束：

- **目标版本必须来自用户**。用户没有明确说版本号时，先用提问工具询问，绝不自行猜测或默认选 LTS。
- **只改 `.nvmrc` 和 `package.json` 的 `engines`**。CI（如 `.gitlab-ci.yml` 的 image）、Dockerfile、`.node-version`、`volta` 字段等其他位置的版本差异，只在最终报告中提醒，一律不修改。
- **不自动 git 提交**。改动留在工作区，由用户检查后自行提交。

## 模式判定

按用户给出的目标路径判定：

- 路径自身含 `package.json` → 单项目模式。
- 路径自身不含 `package.json`，但其一级子目录中存在含 `package.json` 的目录 → 批量模式。
- 两者皆非（路径不存在、无任何子项目）→ 报告并停止，请用户确认路径。

## 单项目模式

### 第 1 步：环境与现状检查

1. `nvm version` 确认 nvm-windows 可用；不可用则报告并停止，不要尝试其他安装方式。
2. `nvm list` 查看已装版本；目标版本已在列则第 2 步跳过安装。
3. 读 `package.json`：`engines.node`、`packageManager` 字段；看项目根目录是否已有 `.nvmrc`。
4. `node -v` 记录当前版本。
5. 扫描其他位置的 Node 版本（`.gitlab-ci.yml` 的 image、`Dockerfile` 的 FROM、`.node-version`、`engines` 之外的 volta 配置），仅记录，供第 6 步报告使用。

### 第 2 步：安装并切换 Node

1. 目标版本未安装时执行 `nvm install <版本号>`。
2. 执行切换前，必须告知用户：**nvm-windows 是整台机器全局切换**，切换后所有项目都会用新版本；若有其他项目依赖旧版本 Node，完成后需要手动切回。告知后再执行 `nvm use <版本号>`。
3. `node -v` 确认已切换到目标版本。

### 第 3 步：更新核心两处

1. `.nvmrc`：存在 → 内容更新为新版本号；不存在 → 不创建。
2. `package.json` 的 `engines.node`：沿用项目现有写法风格，只改数值：
   - `>=X.Y.Z <N` 风格（如 `>=22.22.3 <25`）→ 下界改为目标版本，上界改为目标大版本 +1（如升到 `24.10.0` → `>=24.10.0 <25`）。
   - `^`、`~`、`=` 等其他风格 → 保持原前缀，更新版本数值。
   - 项目没有 `engines` 字段 → 询问用户是否要添加，不要擅自添加（批量模式下汇总询问一次）。

### 第 4 步：重装依赖

按 `packageManager` 字段判定包管理器；无该字段时用 npm：

- `yarn@4` 及以上（Berry）→ `yarn install`；若 yarn 不可用先 `corepack enable`。
- `yarn@1` → `yarn install`。
- `pnpm` → `pnpm install`。

在原 `node_modules` 上直接重装。安装失败且报错指向旧缓存/旧产物时，先向用户说明，再清空 `node_modules` 重装。不手动编辑 lock 文件。

### 第 5 步：验证（有啥跑啥）

读 `package.json` 的 `scripts`，按顺序检查以下脚本，**存在即运行，失败即停**：

1. `build`
2. `test`
3. 类型检查：`check:types` / `typecheck`（都没有但有 tsc 依赖时，跑 `tsc --noEmit`）
4. `lint`

规则：

- 脚本不存在 = 该项跳过，不是错误。
- 每项记录结果：通过 / 失败 / 跳过。
- 若项目一个验证脚本都没有，至少确认 `node -v` 正确、依赖安装成功，并在报告中说明"项目未定义验证脚本"。
- 验证失败时：摘要报错，判断是否与 Node 版本升级相关（如依赖不支持新 Node、原生模块需重编译），在报告中给出可能原因和下一步建议；**不要擅自改业务代码来修错，也不要擅自降级版本**。

### 第 6 步：输出报告

1. 版本对照：升级前后的 `node -v`、`engines.node`、`.nvmrc`。
2. 改动文件清单（通常为 `.nvmrc`、`package.json`、lock 文件的自动更新）。
3. 验证结果表：build / test / 类型检查 / lint 各自的 通过 / 失败 / 跳过，及失败项的错误摘要与建议。
4. 其他位置版本不一致提醒：列出第 1 步扫描到的 CI、Dockerfile 等仍指向旧版本的文件，提醒用户自行决定是否更新。
5. 提醒：改动未提交，由用户检查后自行 git 提交；nvm-windows 全局已切换，其他项目若需旧版本需手动 `nvm use` 切回。

## 批量模式

批量 = 发现 → 预检确认 → 切换一次 Node → 逐项目执行单项目模式第 3~5 步 → 汇总报告。

### 第 1 步：发现项目

扫描父目录的**一级子目录**，满足以下条件的视为前端项目：

- 子目录内存在 `package.json`。
- 排除 `node_modules`、以 `.` 开头的目录、无 `package.json` 的目录。

### 第 2 步：预检并确认

逐项目收集现状，汇总为清单后**必须经用户确认才动手**：

| 收集项 | 说明 |
|---|---|
| 当前 `engines.node` / `.nvmrc` | 判断该项目的版本约束是否兼容目标版本 |
| `packageManager` | 预判依赖安装方式与耗时 |
| git 工作区状态 | 有未提交改动的项目标记出来，提醒用户改动会混在一起 |
| 其他位置版本（CI/Docker） | 供报告提醒 |

确认清单中须包含：项目总数与名单、目标版本、nvm 全局切换警告、预计耗时较长（每项目都要装依赖 + 跑验证）。用户可在此时剔除不想升的项目。

### 第 3 步：安装并切换 Node

整个批次只切换一次：`nvm install <版本号>`（未装时）→ 告知全局切换影响 → `nvm use <版本号>` → `node -v` 确认。

### 第 4 步：逐项目升级

对每个项目依次执行单项目模式的第 3 步（改核心两处）→ 第 4 步（重装依赖）→ 第 5 步（验证），并遵守：

- **单个项目失败不中断批次**：记录失败原因与已完成的步骤，继续下一个项目。
- 每个项目处理完立即记录结果，不要等全部结束后凭记忆汇总。
- 中途用户中断时，输出已完成部分的结果表。

### 第 5 步：汇总报告

1. 总表：每项目一行 —— `engines`/`.nvmrc` 前后对照、build / test / 类型检查 / lint 各项结果（通过 / 失败 / 跳过）、整体结论（成功 / 部分失败 / 失败）。
2. 失败项目明细：错误摘要、是否与 Node 升级相关的判断、建议。
3. 聚合提醒：所有项目中 CI/Docker 等位置仍指向旧版本的清单；有 git 未提交改动的项目清单。
4. 全局提醒：改动均未提交，需用户逐项目检查提交；nvm 全局已切换，其他目录的项目若需旧版本需手动 `nvm use` 切回。
