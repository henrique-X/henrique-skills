# Testcase Generator

根据 git commit message 关键字，查找相关提交，分析代码变更及其调用链上下文，生成结构化测试用例。

## 工作流程

### Step 1: 获取关键字

从用户输入中提取 git commit message 关键字（如 `TG-9537`、`feature/login` 等）。

### Step 2: 查找提交记录

```bash
# 查找所有分支中包含关键字的提交（排除 merge 提交）
git log --all --oneline --no-merges --grep="<keyword>"
```

若结果为空，尝试不排除 merge 提交：
```bash
git log --all --oneline --grep="<keyword>"
```

### Step 3: 查看变更文件范围

对每个非 merge 提交查看变更文件：
```bash
git show <commit-hash> --stat
```

### Step 4: 查看具体代码变更

逐个查看每个功能提交的 diff：

- **小 diff（< 5000 行）**: 直接 `git diff <hash>^..<hash>` 查看
- **大 diff（>= 5000 行）**: 分段读取，重点关注：
  - 新增/删除的文件
  - 新增的函数/方法
  - 修改的组件 props 或接口参数
  - 变更的业务逻辑

对于同一功能有多个分支版本（如 sz_dev、5.3.1）的情况，选择 **最新的** sz_dev 分支提交作为主要分析对象，忽略重复的分支版本。

### Step 5: 追踪调用链上下文

在分析 diff 之后，对变更中涉及的 **关键标识符** 进行上下游追踪，以获取完整上下文。这是生成准确测试用例的关键步骤。

#### 5.1 提取需要追踪的标识符

从 diff 中识别以下类型的标识符：

| 类型 | 示例 | 追踪目的 |
|------|------|---------|
| 函数/方法名 | `onDisplayNameChange`, `handleOk` | 找到所有调用方 |
| 组件名 | `BranchCommitModal`, `CommitModal` | 找到所有使用该组件的父组件 |
| 接口/API 函数 | `getGpgKeys`, `gitCommit` | 确认接口定义和调用点 |
| State/变量名 | `gpgKeys`, `useGpg` | 确认状态如何被消费 |
| Props 参数 | `projectId`, `branchName` | 确认参数来源和传递链 |
| 自定义 Hook | `useCommitBranch`, `useDataPool` | 找到所有调用该 hook 的组件 |

#### 5.2 追踪上游（谁调用了变更的代码）

```bash
# 搜索函数/方法被调用的位置
grep -rn "functionName(" --include="*.tsx" --include="*.ts" --include="*.jsx" --include="*.js"

# 搜索组件被使用的位置
grep -rn "<ComponentName" --include="*.tsx" --include="*.jsx"

# 搜索 hook 被调用的位置
grep -rn "useHookName(" --include="*.tsx" --include="*.ts"
```

优先使用 Grep 工具进行搜索，效率更高。

#### 5.3 追踪下游（变更的代码调用了什么）

```bash
# 在变更文件中搜索 import 语句，确认依赖
grep -n "^import" <changed-file>

# 搜索变更函数体内的调用
grep -n "serviceName\.\|apiFunction\|fetchFunction" <changed-file>
```

#### 5.4 读取关键上下文文件

对于追踪到的关键上下游文件，使用 Read 工具读取相关代码片段（不需要读整个文件，读取相关函数/方法即可），重点关注：

- **调用方代码**：确认参数如何传递给变更的函数/组件
- **被调用方代码**：确认接口签名、参数结构、返回值结构
- **兄弟组件**：如果变更的组件与其他组件共享状态或 props，确认联动关系

#### 5.4 追踪深度控制

- 追踪 **不超过 2 层** 调用链（变更代码 → 直接调用方/被调用方 → 再往上一层即可）
- 如果追踪结果超过 5 个文件，只读取与变更逻辑最相关的 5 个文件
- 对于纯 UI 样式变更（如 `hasBorder={true}`），不需要追踪调用链
- 对于以下类型的变更，**必须追踪调用链**：
  - 新增/修改了接口调用（追踪接口定义和调用点）
  - 新增/修改了组件 props（追踪所有使用该组件的位置）
  - 新增/修改了自定义 hook（追踪所有调用该 hook 的组件）
  - 修改了共享 state 或 context（追踪所有消费者）
  - 新增/修改了工具函数导出（追踪所有 import 方）

### Step 6: 分析代码变更并生成测试内容

综合 diff 和调用链上下文，按以下三个维度生成测试内容：

#### 维度一：核心功能测试

改动直接影响的业务逻辑和功能点。

**分析要点：**
- 新增功能 → 验证完整的主流程是否正常工作
- 接口参数变更 → 追踪接口定义和所有调用点，验证参数正确传递、返回值正确处理
- 条件逻辑变更 → 追踪上下文确认触发条件能否被用户操作覆盖
- 跳转/路由变更 → 追踪目标页面，验证 URL 参数被正确接收和使用
- 状态管理变更 → 追踪所有状态消费者，验证数据流正确
- 新增字段/属性 → 验证 UI 显示和表单提交；追踪调用链确认所有消费方都正确处理新字段

#### 维度二：边界与异常测试

针对改动引入的边界值、异常处理、空值等。

**分析要点：**
- 空值/null/undefined → 输入为空时是否有正确兜底
- 数组越界/空数组 → 列表为空时 UI 是否正常，索引访问是否安全
- 类型边界 → 数字最大/最小值、字符串超长、特殊字符
- 异步异常 → Promise reject、网络超时、接口错误响应
- 并发/竞态 → 快速连续操作（如双击提交、重复请求）是否有防护
- 权限边界 → 无权限、未登录、跨组织访问时的表现
- 数据类型不一致 → 后端返回类型与前端预期不一致时的容错

#### 维度三：影响范围/回归测试

这次改动可能会间接影响到哪些已有功能。

**分析要点：**
- 组件 props 变更 → 追踪所有父组件，确认无遗漏
- 字段重命名 → 追踪所有引用处，确认全部已更新
- 工具函数修改 → 追踪所有调用方，确认行为变化不影响现有逻辑
- 共享状态/Context 变更 → 追踪所有消费者，确认状态结构兼容
- 样式变更 → 检查是否有其他组件复用了被修改的样式类
- 路由变更 → 检查导航、面包屑、权限守卫是否正常
- 配置变更 → 检查默认行为是否被意外改变

每个测试项包含：

| 字段 | 说明 |
|------|------|
| # | 编号 |
| 测试内容 | 简要描述需要测试的内容 |
| 验证点 | 需要确认的具体检查项 |

生成 Markdown 格式报告，结构如下：

**涉及文件：**
- `文件路径` — 变更说明

---
