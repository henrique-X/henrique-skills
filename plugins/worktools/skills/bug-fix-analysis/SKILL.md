# Bug Fix Analysis

在 bug 修复完成后，对本次修改进行系统性分析，输出结构化的修复报告，覆盖根因、改动、影响范围和 breaking change 风险。

## 工作流程

### Step 1: 确定分析范围

从用户输入或当前分支名中提取 `TG-XXX` 编号（如 `hangxuan/console_TG-9537/SZ_dev` -> `TG-9537`），或由用户直接指定 commit hash。

如果用户未提供任何信息，使用当前分支与目标分支之间的 diff：

```bash
# 获取当前分支最新提交
git log -1 --oneline

# 获取与目标分支的差异提交
git log origin/<target>..HEAD --oneline --no-merges
```

### Step 2: 查找相关提交

```bash
# 按 TG 编号查找所有相关提交
git log --all --oneline --no-merges --grep="<TG-XXX>"
```

若结果为空，不排除 merge 提交重试：
```bash
git log --all --oneline --grep="<TG-XXX>"
```

### Step 3: 查看变更概览

对每个提交查看变更文件范围：
```bash
git show <hash> --stat
```

统计变更文件数量、新增/删除行数，形成概览。

### Step 4: 分析具体代码变更

逐个查看每个提交的 diff：

- **小 diff（< 500 行）**：直接 `git diff <hash>^..<hash>` 完整查看
- **大 diff（>= 500 行）**：分段读取，重点关注：
  - 新增/删除的函数和方法
  - 修改的条件判断和业务逻辑
  - 变更的接口签名、props、参数
  - 新增/删除的文件
  - 配置变更

### Step 5: 根因分析

根据 diff 内容，分析 bug 产生的根本原因：

1. **定位 bug 点**：找出导致 bug 的具体代码位置（哪一行、哪个函数、哪个条件分支）
2. **分析触发条件**：什么情况下会触发这个 bug（特定输入、特定状态、特定操作序列）
3. **理解修复方式**：修复代码是如何解决这个问题的（替换逻辑、增加校验、修正条件、补充处理）

### Step 6: 追踪调用链与影响范围

对变更中涉及的 **关键标识符** 进行上下游追踪。

#### 6.1 提取需要追踪的标识符

从 diff 中识别：

| 类型 | 示例 | 追踪目的 |
|------|------|---------|
| 函数/方法名 | `handleSubmit`, `validateInput` | 找到所有调用方（上游影响） |
| 组件名 | `UserForm`, `DataTable` | 找到所有使用该组件的父组件 |
| 接口/API 函数 | `getUserList`, `submitForm` | 确认接口契约是否变化 |
| State/变量名 | `formData`, `isValid` | 确认状态消费链 |
| Props 参数 | `onSubmit`, `disabled` | 确认参数传递链 |
| 自定义 Hook | `useValidation`, `useSubmit` | 找到所有调用该 hook 的组件 |
| CSS 类名/样式 | `.container`, `style={...}` | 确认样式变更是否影响其他组件 |
| 路由路径 | `/api/users`, `/dashboard` | 确认路由变更影响 |

#### 6.2 追踪上游（谁调用了变更的代码）

```bash
# 搜索函数/方法被调用的位置
rg -n "functionName" --type js --type ts --type jsx --type tsx

# 搜索组件被使用的位置
rg -n "<ComponentName" --type tsx --type jsx

# 搜索 hook 被调用的位置
rg -n "useHookName\(" --type ts --type tsx
```

#### 6.3 追踪下游（变更的代码调用了什么）

对修改的函数/方法，查看它内部调用的其他函数是否受到影响。

#### 6.4 影响范围评估

根据追踪结果，将影响分为三级：

| 级别 | 定义 | 标准 |
|------|------|------|
| 直接影响 | 变更代码的直接调用方 | 调用了被修改函数/组件的代码 |
| 间接影响 | 调用方的调用方 | 通过中间层间接受影响 |
| 潜在影响 | 共享状态或样式的代码 | 通过共享变量、context、样式表等间接受影响 |

### Step 7: Breaking Change 评估

逐项检查以下 breaking change 风险：

#### 7.1 接口契约变更
- 函数签名变化（参数数量、类型、顺序）
- 返回值类型变化
- 组件 props 增删改
- API 接口请求/响应结构变化

#### 7.2 行为变更
- 条件判断逻辑变化（可能导致之前通过的场景现在不通过，或反之）
- 默认值变化
- 错误处理方式变化（静默失败 -> 抛异常，或反之）
- 异步行为变化（同步 -> 异步，或反之）

#### 7.3 数据变更
- 数据库 schema 变更
- 缓存 key 变更
- 状态管理结构变更
- 文件格式变更

#### 7.4 依赖变更
- 新增/删除/升级第三方依赖
- 内部模块依赖关系变化

#### 7.5 评估结论

对每项风险给出结论：

| 结论 | 含义 |
|------|------|
| 无 breaking change | 修改完全向后兼容 |
| 低风险 | 可能影响边缘场景，需关注 |
| 中风险 | 会影响部分调用方，需要同步修改 |
| 高风险 | 会破坏现有功能，必须同步修改所有调用方 |

### Step 8: 生成修复报告

输出结构化的 Markdown 报告：

```markdown

- TG 编号: TG-XXXX
- 分支: xxx -> xxx
- 提交数: N
- 变更文件数: X

## Bug 概述
[一句话描述这个 bug 是什么]

## 根因分析

[导致 bug 的具体代码位置和原因]

[什么情况下会触发这个 bug]

[修复代码是如何解决问题的]

## 修改内容

### 变更文件清单

| 文件 | 变更类型 | 说明 |
|------|---------|------|
| src/xxx.js | 修改 | 修正了 xxx 逻辑 |
| src/yyy.js | 新增 | 添加了 xxx 处理 |

[逐个说明每个重要变更的上下文和意图]

## 影响范围

[被修改代码的直接调用方]

[通过中间层间接受影响的部分]

[共享状态/样式等可能受影响的部分]

## Breaking Change 评估

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 接口契约变更 | 无/有 | ... |
| 行为变更 | 无/有 | ... |

```

## 注意事项

1. 分析时以代码事实为准，不要猜测。如果无法确定某个影响，标注为"待确认"
2. 大 diff 要分段读取，不要遗漏关键变更
3. 追踪调用链时使用 rg（ripgrep）优先，效率更高
4. Breaking change 评估要保守：宁可多报风险，不要漏报
5. 如果有多个分支版本的同一提交（如 sz_dev、5.3.1），选择最新的 sz_dev 分支作为主要分析对象
